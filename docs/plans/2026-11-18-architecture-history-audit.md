## 一、先明确系统究竟需要做什么

用户交付一段拉伸试验视频，系统要回答三个可以独立验证的问题：观察是否属于指定视频、时间段和视觉部署；哪些观察足以支持断裂、未断裂或拒判；哪些字段有足够证据向用户发布。一次断裂发生在片段内与片段开始时已经断裂，对时间定位有不同意义。一个片段未见断裂，也只说明该片段中的观察。每个片段最多稀疏选取 8 帧，五窗阴性是一条项目定义的发布规则，其检测能力仍须实测。

| 责任 | 当前正常路径 | 接手时必须保住的约束 |
|---|---|---|
| 接收任务、解释需求 | CLI / FastAPI → `runner.run_one` → 意图识别与结果投影 | CLI 和 Web 共用一套结论；用户可只问部分字段；用户原话不进入视觉提示 |
| 建立一次可信观察 | 裁剪、实际帧时间戳、HTTP 预检、逐轮部署身份、严格解析 | 输入身份可追溯；模型异常、传输故障、缺帧表应能分别诊断；冻结配置固定本次协议 |
| 从观察得出视频结论 | `IterativeAgent`、`V41EventBounds`、`FinalOutput` | 规划器提议；程序确认覆盖、局部正证据、同窗复查和单调边界；断裂成立时仍可缺时间、机制或位置 |
| 复核过程与实验结论 | Web 回放、运行日志、冻结评测、交付组件清单 | 用户展示、实验评分、服务身份各有读者；历史结果须可复核；运行测试、服务联通和模型质量需要各自证据 |

**根因有三层。** 第一，运行时在同一个字典流中同时保存“下一步可以去哪里采”“这一次实际观察了哪里”和“事件的可信边界”。代码已有边界对象，但进入阴性覆盖时仍会读错对象。第二，V2 与 V4.1 的观察靠字典缺键和字符串猜测，合法的 V4.1 记录必然缺失某些 V2 字段，缺键因而能被解释成“模型说无法判断”。第三，实验与交付的冻结信息分散于代码、配置、清单和历史报告。一次改变若只更新其中一处，其他入口仍能给出看似完整的结果。最有效的简化单位是一次有明确定义的观察和一次有明确定义的裁决。

入口可从 [Runner](../../agent/runner.py)、[迭代循环](../../agent/iterative_agent.py)、[事件边界](../../agent/v4_1_evidence.py)、[视觉契约](../../agent/contracts/tensile_vlm_v4_1.json) 和 [公共结果](../../agent/schema.py) 开始读。

## 三、影响结果可信度的发现

以下使用真实 `IterativeAgent.run()`，在其正常依赖入口提供可控的规划回复、裁剪替身及带部署元数据的视觉输出。除另行注明，视频时长为 40 秒。它们证明这些结果可达，真实视频上的触发频率和对召回的贡献仍待测量。

| 优先级与发现 | 复现或代码证据 | 修改建议与验收 |
|---|---|---|
| P0 · 局部阴性可导致整片阴性 | 全片“发生断裂”使状态进入 `NARROWING`，可信范围仍为全片。随后实际采样 [10,20] 得到“未断裂”。`_transition_v4_1` 用候选区间判断全局，转入 `COVERAGE`。五窗再报阴性即发布 `no_fracture`，历史仍有 1 个阳性。对照组为全片阴性＋五窗阴性，正常在 6 次视觉观察后结束。 | 依据实际取样范围及本轮用途识别全片观察；用明确规则裁决尚未解释的正负冲突。回放前者不得以局部观察启动全片阴性覆盖；后者必须仍能结束。 |
| P0 · 拒判原因可脱离证据 | 预算 10，首轮提议 `unrecognized/max_rounds` 直接成功，0 次视觉调用。两次同窗“发生断裂”后提议 `video_anomaly` 也成功，输出 `special_case=null`。V4.1 无 `has_fracture` 字段，在 `_has_consistent_special_recheck` 中被 V2 的 `.get(...) is None` 条件命中。 | 按选定契约解释观察；预算、非法输出、冲突和特殊样例均以实际事实判定。对“未夹紧”“视频异常”和一般不可判定分别匹配同窗签名；在正常收口和耗尽收口两条路径运行相同回放。 |
| P0 · 合法观察可令调度停滞 | 连续四次“已断裂”或“临界未断裂”，规划器每次申请局部采样，实际四次均被覆写为 [0,40]，产生 4 次空交集冲突后耗尽。另一路为全片阴性 → 首个覆盖窗“无法判断” → 同窗复查转阴；9 轮后仅完成 1/5，持续重采 [0,10]。 | 显式保存首次全片检查是否完成。首次方向落到视频边缘时，明确允许哪种局部核查或有据拒判；已解决的同窗复查必须消费掉等待状态。验收同时保留单调边界、两次一致异常和正常五窗。 |
| P0 · 明确指定的回滚协议可失效 | 真实 CLI、4 秒合成 MP4、真实 ffmpeg、确定性规划器与 mock 视觉：给 V4.1 配置加 `--contract-version tensile-vlm/v2`，实际预检身份和公开结果仍是 V4.1。CLI 写环境变量，客户端优先读 YAML。旧 CLI 测试仅断言解析到参数。 | 将显式版本并入任务有效配置，贯穿提示、预检和结果。选择 V2 时只能进入 V2 预检，连接 V4.1 服务应失败；对两个方向、单视频和批量入口均验收。 |
| P0 · 基础设施失败可能被计为业务拒判 | 同时提供非法视觉内容和缺失预处理元数据，连续两轮得到 `unrecognized/max_rounds`。在 `_execute_sample_and_infer` 中，解析失败先返回，身份/帧表验证在后。另在 `_finalize`，程序组装的最终对象若违反契约，会被广义捕获并改成 `invalid_model_output`；配置容差大于 1 秒与公开结果的 1 秒上限可触发这一矛盾。 | 单轮分开记录传输/身份、解析和有效观察，明确故障优先级；保留原始双重原因。结果组装失败走内部错误信封，合法拒判走业务结果。配置入口拒绝非有限数及超出公开上限的容差。 |
| P1 · 实验比较的证据门不对称 | 三策略实验的 A/B 直接读取 HTTP 客户端 `result.ok`，C 经过 Runtime 的逐轮元数据校验。实际向 A 路径提供合法“发生断裂”但无预处理元数据的响应，仍映射为 `fracture`。主链在相同条件下拒绝这条观察。 | 三组共用最小的逐轮身份与帧表校验。A 保留单次预测，B 保留固定扫描，C 保留 Agent 的决策和终止规则。相同坏输入应记为相同的传输/身份失败。 |
| P1 · 标签缺失可能悄然改变评分 | `normalize_ground_truth({"video_id":"synthetic"})` 实测返回 `has_fracture=True`。冻结报告已记录中文列头使时间、机制、位置和特殊样例指标缺测；当前代码对缺列或未识别类别的默认路径可能把未知变成正例。 | 新评测协议在评分前验证表头、标签全集和逐指标有效分母；未知值必须可追踪。保留原分数，补算结果使用新协议号并报告差异。 |
| P1 · 交付“通过”的对象容易被误读 | 本仓轻量校验通过，跨仓校验返回 `canonical model component hash mismatch`。比较两份模型清单只见受管路径由 `workspace/models/…` 变为 `models/…`；声明的权重聚合哈希相同，本次未重新散列权重。`generate_delivery_bundle.py` 直接写入包括真实 GPU、测试和 Git 同步在内的通过标志。校验器检查祖先、文件和既有记录，一次生成无法提供新测量。 | 冻结旧交付；新交付从实际测试、身份和联调记录读取状态，绑定两侧提交、产物和日期，缺失标为未验证。确认新路径后对齐清单。仅重新运行生成器不能完成新交付验收。 |

### 容易在交接时漏掉的边界

- **任务配置与诊断。** `run_one` 在读取指定配置、CLI 覆盖和 Web 模型快照前调用 `parse_user_intent`，后者独立读取全局配置并创建客户端。确定性预验收仍可能先尝试本机的意图模型。主配置写 local/0.2，若干缺省分支仍是 remote/0.7；Runner 写 `original_fps`，提示读 `fps`。Doctor 对非确定性后端统一检查 Ollama，包括远程配置。建议一次解析配置并显式传入各阶段，按生效后端诊断，区分 FPS 未知与零值。[任务装配](../../agent/runner.py) · [意图](../../agent/interaction.py) · [提示](../../agent/prompts.py) · [诊断](../../agent/doctor.py)
- **规划器看到的历史。** 强制调度轮会写入 Runtime 历史与新用户上下文，却不创建 `role=tool` 消息。确定性规划器仅从工具消息重建历史，重新枚举索引，并用正则从中文提示中提取候选区间。自动覆盖中途发现阳性后，同一索引可能指向不同观察；改提示措辞还可能触发默认区间 [0,1]。将同一份结构化历史、稳定证据编号和有效阈值直接传给确定性策略；只在 LLM 适配层渲染文本。并行保留两种策略直到同条件评估完成。[规划器](../../agent/llm.py) · [单轮执行与历史](../../agent/iterative_agent.py)
- **Web 任务、历史与回放。** 前端先取历史、再开仅推实时事件的 SSE，中间和断线期间均有漏事件窗口；服务端在线程池运行推理，回调直接操作事件循环的队列。reducer 浅拷贝顶层后更改旧 `rounds` 数组和元素；界面可用最终任务快照兜底，过程仍可能不完整。历史文件和私有路径索引分别直接覆盖写，重启恢复依赖两者。建议同一任务采用连续事件号，先持久化再由事件循环投递，支持按游标补读；用不可变 reducer 测重复、断线和切换任务。历史写入采用原子替换和启动对账，保留旧格式读取。以上是代码路径判断，本轮未做浏览器断线与断电压测。[Web 服务](../../agent/web_api.py) · [回放与订阅](../../web/src/hooks/useAgentTaskEvents.ts) · [最终展示](../../web/src/components/ActiveAnalysisWorkspace.tsx)
- **采样与诊断产物。** 每轮重新探测同一源视频及全部帧时间戳，再编码 clip；不同目录中的同名视频或取整到相同两位小数的窗可落到同一输出路径。逐轮诊断按视频 ID 写，CLI 重跑也会复用 trace 名称。单 Web worker 降低并发概率，CLI/重复实验仍可覆盖旧路径。按运行 ID 隔离，保留视频 ID 作关联，源 PTS 只在同次运行缓存；用相同输入对比帧映射和哈希，再实测节省的时间。决策端已有最多两次传输重试，trace 却总写 `retry_count=0`。预算、调用成本与延迟统计应分别记录逻辑轮次和实际请求。[裁剪](../../agent/sampling.py) · [决策客户端](../../agent/llm.py) · [传输记录](../../agent/llm_trace.py)
- **错误与公开投影。** Web 的 `_apply_runner_result_to_task` 把显式 `ok=False` 以外的对象都先标为完成；不支持的结果信封会被 `_normalize_result` 投影成 V2 拒判。Runner 的失败回调又独立于运行循环的事件隔离；辅助 evidence 响应在成功返回后直接读取首个 choice。建议共享一次版本化公开投影；新执行遇到不合法信封走失败，旧历史按版本读。附加证据解析失败只让该证据不可用。测试覆盖空信封、空 choices、失败监听器。[Web 结果映射](../../agent/web_api.py) · [Runner](../../agent/runner.py) · [视觉客户端](../../agent/inference.py)

## 六、真实接手成本与实施顺序

以下是**单名熟悉 Python、HTTP、React 的资深工程师**的估算，假设此前没有材料拉伸语义和本项目知识。一个人日按 8 小时计。累计里程碑各自包含前一项；修复批次的人日另列。前提是有可用的本地工具链，真实服务阶段由项目方提供正常权限、GPU 服务和一条开发视频。缺少这些条件会延长日历时间。

| 接手里程碑 | 累计人日 | 如何证明已经接手 |
|---|---:|---|
| 能独立启动、定位入口 | 0.5–1 | 从选定提交建立 Python/Node 环境，跑 Python 与 Web，使用合成视频和真实裁剪跑通确定性＋mock 视觉，指出运行结果与模型质量的区别。 |
| 能解释一条新的正常/失败轨迹 | 2–4 | 追到部署、实际采样窗、证据索引与最终结果；解释特殊样例、局部阴性、时间不可用和传输失败；能区分 V2 回滚、实验分支和当前默认。 |
| 能安全交付第一次跨层修复 | 4–7 | 修复一个已复现的裁决或配置问题，有原缺陷回放；CLI/Web/公开结果/冻结对照的影响均已说明，以真实守卫回归。 |
| 能独立负责跨仓中间交付 | 6–10 | 拿到部署后做开发视频 smoke，核对双仓清单、测试结果、冻结版本，演示错误身份拒绝和回滚步骤。另计服务排队和权限等待。模型训练、提升到生产准确率及新的独立质量验收需另估。 |

**计算资源成本。** 稳定全片阴性的实测控制轨迹需要 6 次逻辑视觉观察，当前 V4.1 自动调度仅向规划器请求 1 次；真实产品还可能另有意图调用、应用户要求的视觉说明调用及传输重试。若做 30 个开发视频、两种规划器、每条每组最多 10 轮的配对实验，主视觉逻辑观察上限是 600 次。失败、提前收口、附加调用和重试改变实际 GPU/API 请求数。现有材料不足以给出本机当前 GPU 小时或费用。先在开发样本上分别量出裁剪、主视觉、证据、意图与规划耗时及重试，再用实测均值与样本数估算。

| 实施批次 | 建议投入 | 范围与验收 |
|---|---:|---|
| A · 先修结论与回滚 | 3–5 人日 | 以本报告的正负冲突、异常签名、预算、复查恢复、全片边界、元数据失败及 CLI 版本复现建立回放，再修状态转换与配置优先级。每条都要断言下一次实际采样窗、实际视觉次数、结果信封；覆盖正常五窗与真实异常作对照。 |
| B · 让评测与交付可信 | 2–4 人日，另计 GPU | 对齐三策略逐轮有效性与标签分母，检查任务配置、身份和真实请求数。为下一次交付绑定独立验证记录。历史验收留原样，先在开发集配对比较确定性和本地 LLM；同时报告断裂召回、阴性误报、拒判、时间命中和成本。未获得稳定收益前维持默认策略。 |
| C · 兑现低风险清理 | 0.5–1.5 人日，另计训练侧断言核对 | 第一小批删主线框架依赖和无消费者的内部状态；第二小批处理训练测试与 V3/V4。记录预期消失的测试数、契约校验和外部路径核对。每批可独立撤销。 |
